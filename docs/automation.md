# Automated SQL ingestion

Automation JSON outcomes expose the destination chart ID and title, plus `entity_properties_changed` and `connection_properties_changed` separately in snapshot delta counts. Entity-property changes describe SQL supplied source or target attributes and visual representations; relationship-property changes describe connection attributes. Each changed record includes its current and previous values and the matching change kind. Run-history CSV/TSV exports include the destination chart ID, entity-property and relationship-property counts, and the current and baseline SQLite schema versions, schema fingerprints, drift flags, and schema-object changes in `delta_json`; JSON deltas retain added, removed, and modified object names with per-object definition fingerprints and added, removed, or changed column names and structural metadata, without storing raw schema SQL or column default values.

## Review and preflight

In **Automation**, **Unreviewed changes or partial data** filters to captures with removals, confidence declines, changed SQL entity or relationship properties, a changed SQLite schema fingerprint, skipped rows with blank or NULL endpoints, or a failed saved schema-stability policy because prior schema metadata is unavailable, when no review mark exists. The queue includes runs that passed configured limits. Expanded review details show prior/current property values, schema fingerprint drift, skipped-row counts, and added, removed, modified, or probable renamed SQLite objects, even when the schema change produced no connection rows. For a partial capture, **Load captured query for validation** loads its database path, series, query, and parameters into SQL Review without running the query. **Validate query** then runs it read-only against the current database and displays fresh skipped-row examples in the transient validation preview. Snapshot history persists the skipped-row count and captured SQL, not the example rows; validation can therefore show current source results rather than reconstructing historical rows. A probable rename is reported only when exactly one removed and one added object of the same type share a definition fingerprint after only the declared object name is normalized; other identifiers and SQL string literals remain significant. It is a hint, not a confirmed rename. Exact schema fingerprints still include object names, and raw schema SQL is not stored. When both captures include object manifests, a schema-stability failure also names up to three changed SQLite objects in the run message, followed by a count of any remaining changes; full fingerprints and object details remain available in review. **Unreviewed failures** remains available for failed runs that have not been explicitly marked reviewed; older runs without a review mark use the analyst comment as the fallback signal. A successful run that skipped rows is marked **PASS · PARTIAL DATA** in the job list and run history; hover or expand the result to see that rows with blank or NULL endpoints were excluded. The configured skipped-row threshold still determines pass or fail. Jobs can set separate maximum counts for changed relationship-property and entity-property records, so SQL drift in transaction values, account status, or endpoint attributes can fail a capture independently of removals, additions, and record counts. Each job can also require an unchanged SQLite schema; this saved policy is enforced by manual, scheduled, replayed, and preflight captures. A first capture establishes the baseline. If a prior snapshot exists but has neither comparable schema fingerprints nor schema versions, the run fails for review instead of treating the schema as unchanged. Run-history search includes effective SQL parameter names and values, making ad-hoc and batch override runs discoverable by the values they used.

Use **Preflight enabled jobs and overrides** to check every enabled query read-only with the current one-run SQL parameter overrides and inspect per-job progress and diagnostics before a batch run. Preflight evaluates each job against its configured destination chart and compares the capture with that chart's prior snapshot. **Require at least one usable connection per job** is enabled by default; turn it off when a valid query may intentionally return no usable links. Enable **Require unchanged SQLite schema during preflight** to fail review when the current schema fingerprint differs from the prior snapshot for the same database and series (schema versions provide a fallback for older snapshots); the first capture has no baseline and passes. These switches apply only to this preflight and do not change saved jobs, scheduled captures, or run history. While a query is active, the progress panel reports elapsed query time and the current job. Choose **Cancel preflight** or press **Esc** to stop a slow or stuck query; this terminates the preflight process and does not change the case or save run history. Completed results show each job's destination and failure details; choose **Repair SQL** for schema errors or **Edit job** for other failures to act on the result directly. The panel focuses the job list on the selected job so it remains visible after editing. Schedule install, check, remove, and preflight results remain visible in the Automation panel for the case that was acted on. Schedule installation separately preflights the saved job parameters before changing the scheduler, so one-run overrides never alter scheduled captures.

CLI `--validate-job` and `--validate-enabled-jobs` also inspect each saved query against its configured destination chart, even when that chart is not active in the case file. They perform read-only captures and do not save the case or run history.

With CLI `--progress`, each preflight status line includes the job's destination chart title, including the 30-second active-query heartbeat. The heartbeat reports elapsed query time, configured timeout, and remaining seconds before the query deadline.

CLI batch progress uses the same chart label for job starts, skipped checkpoints, saved completions, and active-query heartbeats; scheduled runners expose these lines in their platform logs.

When **Repair SQL** opens an editor for schema errors, the schema inventory offers up to five close table/view matches for a missing table, close column-name matches for a missing column, or the objects that define an ambiguous column. For a qualified missing-column reference such as `account.status`, close matches in `account` are ranked first, with other tables retained as fallback suggestions. The repair panel also compares the inspected database with the latest saved capture for the job's chart, database, and series, listing added, removed, and modified schema objects plus column-level additions, removals, and structural changes. It highlights changed objects and removed columns related to the failed reference when possible; when the exact missing column was removed and its object gained columns, those new fields are offered as possible query updates, without rewriting SQL; expand **Review all changed schema objects** to inspect every change, including removed names that are no longer in the live inventory. Select a suggestion to focus its table or view in the inventory, then review and edit the SQL yourself; suggestions never rewrite a query.

During a desktop automation run, choose **Cancel automation** or press **Esc** to interrupt the active read-only SQLite query and stop before starting later jobs. The cancelled job is recorded as failed and its run history is checkpointed; prior completed jobs remain saved and later jobs stay pending. For a batch, resume it from its saved batch ID to retry the cancelled job and run the remaining selection. Closing the desktop window during automation requests cancellation, waits for the active job result to be saved, then closes; completed checkpoints remain available to resume.

The desktop progress panel reports result rows read and blank-endpoint rows skipped during SQL iteration, then switches to chart-application progress with processed relationship and entity counts, and finally reports snapshot finalization. Counts update at most once per second while each phase is active; SQL drivers do not always provide a total row estimate, so the UI reports observed counts rather than a fabricated percentage. This is transient operational feedback and is not stored as case data.

The Automation panel lists every retained batch checkpoint (up to 200), newest first, so older incomplete selections can still be inspected and resumed in the app. The `--list-batches` CLI command remains available for scripting and JSON output.

The Automation job search matches job names, destination chart titles or IDs, database paths, series, SQL text, and saved SQL parameter names and values. `--list-jobs --json` includes each saved job's destination chart ID and title plus its latest run's raw and derived review state; job cards label failed captures as **NEEDS REVIEW** or **REVIEWED**. `--list-runs --json` includes the chart title resolved for each capture alongside its chart ID.

### Sharing and adapting jobs

Export a job package from the Automation panel or with `--export-job`; import it in the panel or with `--import-job`. Version 5 packages include the SQL query time limit; version 4 adds the saved schema-stability policy; version 3 records the destination chart title and exporting case directory when the SQLite database path is relative. The title must match one existing chart in the destination case; if it does not, choose an existing chart from the panel's **Destination chart** menu or pass `--chart <chart-title-or-uuid>` during CLI import. UUID selection disambiguates charts with duplicate titles. Older version 1, 2, 3, and 4 packages remain supported: version 2 records the source case directory, version 3 records the destination chart title and source case directory, and packages without timeout settings use the 15-minute default. Missing schema-stability settings default off. Versions 1 and 2 without a chart title target the active chart. When moving a package and database to another machine or location, pass `--database <path>` during CLI import or set the **Database** override in the panel. Imported jobs are disabled until reviewed.

SQL Review saved-search definitions use a separate definition-only package format: `--export-sql-search` and `--import-sql-search`. Import adds a case-local query draft and does not execute it, capture data, or create an Automation job. See [moving a saved search between cases](sql-ingestion.md#move-a-saved-search-between-cases). Load the selected definition before preparing its automation draft; the action stays disabled if the selected catalog item differs from the loaded search. For an unseeded search, choose **Prepare automation draft** to retain its typed SQL parameter values, clear any stale validation preview, and set a prospective job name. For chart-seeded searches, choose **Prepare unseeded automation draft**; the app removes only the bound chart-ID parameter value, leaves the SQL predicate unchanged, clears the old validation preview, and warns that the predicate may still filter results. In both cases, review or edit the SQL and validate the current unseeded query again. Then use **Save and review in Automation**; the created job starts disabled, and the original saved search is unchanged. Draft preparation does not run SQL, create a job, schedule a capture, or persist case changes.

Set **SQL query time limit** in the Automation job editor to stop a slow saved query after 1 to 1,440 minutes; the default is 15 minutes. The same per-job limit applies to query validation, desktop and command-line captures, replays, batch resumes, scheduled runs, and installer preflight. Timed-out captures produce a failed run record, and any completed job checkpoints remain available. JSON outcomes and run-history exports include the effective limit for audit and replay.

CLI export and import JSON responses include the destination chart ID and title so scripts can confirm which chart received the job.

### One-run overrides

For an ad-hoc desktop run, expand **One-run SQL parameter overrides**. Enter `name=value` lines for a single job, or scope each line as `Job name or UUID::name=value` for a batch. The panel echoes the effective override lines and checks typed values before enabling a run, so malformed `int:`, `real:`, or `bool:` values fail before a job starts. Scoped selectors must match exactly one enabled job in the chosen batch, and a job/parameter pair can appear only once. Overrides are retained in each run's effective configuration for replay and audit, then clear from the editor. Opening another case or creating a new case also clears the transient overrides so values cannot carry across investigation contexts. They do not modify saved jobs or scheduled captures.

Use the explicit `text:` type when leading or trailing spaces are significant. Text after the `text:` prefix is preserved exactly; for example, `account_code=text:  A7 ` binds two leading spaces and one trailing space. Parameter summaries display spaces as `␠` and tabs as `⇥` so exact values remain visible in override, job, run, and snapshot details. Unprefixed values keep trimming surrounding whitespace for convenience.

## Build and preview queries

The SQL schema builder also recognizes common payment and account endpoint names, including `payer`/`payee`, `debit_account_id`/`credit_account_id`, `origin_account_id`/`destination_account_id`, and `buyer`/`seller`; inspect the generated endpoint mappings before applying a template.

Skipped-row examples retain source and target entity IDs when the SQL query returns them. A blank joined display value with a populated ID can point to a missing endpoint row or an outdated join; use the ID to inspect the source data before adjusting the query.

The validated query preview shows up to eight rows with endpoint names and source IDs, custom source/target attributes, relationship, direction, date, confidence, evidence, and SQL supplied source notes. When source or target values are blank or NULL, **Skipped row examples** shows up to eight affected rows with their connection IDs and endpoint values. These examples remain only in the validation preview and are not written to the case. A prominent result-quality label distinguishes usable results, partial skips, empty results, and cases where every row was skipped, even when a zero-row query passes configured limits. The preview reports removals and confidence declines against the previous capture in the same series, labels a first capture as the baseline, and lists up to eight changes of any type in a **Change preview** with typed endpoints, stable connection IDs/keys, before/current confidence and dates, and evidence/source-note values on hover. Deltas distinguish endpoint entity-property changes from relationship-property changes. Regression, addition, entity-property, and relationship-property counts are reported separately; configured limits apply independently to regressions, additions, relationship-property changes, entity-property changes, and skipped rows. A first capture has no comparison deltas. Each successful capture records SQLite `schema_version` and a deterministic fingerprint of user-defined table, view, index, and trigger definitions in the same read transaction as its query. SQL Review and automation flag fingerprint drift between the selected baseline and current capture, even when there are no connection-row changes; the SQLite schema version remains a separate counter. Use **Regressions only** in the preview to focus on removals and confidence declines. The preview is horizontally scrollable for wide schemas. In **SQL regressions**, set optional automation capture limits, validate the current query and enter a job name before using **Save and review in Automation** to carry the database, series, query, parameters, and capture limits into a repeatable job without re-entering them. Expand **Automation capture limits** to set optional minimum confidence (1–3), minimum/maximum connections, regression, new-connection addition, relationship-property-change, entity-property-change, or skipped-row thresholds before validating. A confidence floor rejects any captured connection below the selected rating; the validation preview reports how many fall below it. Minimum connections cannot exceed a configured maximum; contradictory limits are rejected during save, validation, and package import. This handoff is enabled only for a usable result with no skipped endpoints and passing capture limits; the new job starts disabled until you review and enable it in Automation; disabled rows are labeled and expose Validate/Edit actions.

In both the automation editor and one-off SQL snapshot panel, **Build query from schema** inspects the configured SQLite file read-only and stages templates for tables or views with recognizable source and target columns, including common `src`/`dst`, `start_*`/`end_*`, `actor`/`object`, `sender`/`recipient`, `sender_account_id`/`recipient_account_id`, `subject`/`object`, and `originator`/`recipient` conventions. It maps common `relationship_type`, `relation_type`, `edge_type`, `connection_type`, `interaction_type`, `event_type`, `transaction_type`, `transfer_type`, `transaction_kind`, `transfer_kind`, `predicate`, and `action` fields into the snapshot columns. Date detection includes `event_date`, `event_time`, `event_at`, `occurred_at`, `occurred_on`, `transaction_date`, `transfer_date`, `effective_at`, and `activity_date`; confidence also recognizes `confidence_score`, `confidence_level`, `strength_score`, and `reliability`; evidence, notes, and endpoint type mappings recognize common citation, URI, comment, entity-type, and kind columns. For foreign-key joins, it uses common display fields such as names, usernames, `owner_name`, or email addresses, and combines first/given and last/family name columns when available. On joined endpoint tables, columns prefixed `attribute_`, `entity_attribute_`, or `property_` become source or target entity attributes in the generated query. Relationship rows can use `source_attribute_*` and `target_attribute_*` for endpoint properties, and `connection_attribute_*` or `link_attribute_*` for relationship properties. The template review lists endpoint mappings, connection ID, common connection fields, and custom attribute projections by destination alias and source expression; when no connection ID is detected, identity is derived from canonical typed endpoints, relationship, and direction, and duplicate parallel rows are rejected. Generated templates sort by stable endpoint identity when available (otherwise endpoint labels), then relationship and connection ID when available, with every projected value as a final tie-break. This makes row order repeatable when records share endpoints but differ in direction, dates, evidence, notes, or attributes. It also shows ingestion defaults for undetected relationship, confidence, direction, and entity-type fields. Inspect these before applying the template. If no display field is recognized, the table-scoped key becomes the endpoint value. Generated stable endpoint IDs are scoped to the referenced table and encode SQLite storage types, so equal local keys in different tables remain distinct. Choose a source to review its detected source and target name expressions, stable endpoint ID expressions, and generated SQL; if a stable ID is unavailable, the mapping summary says so and notes that ingestion will reconcile by name and type. The inspected table/view inventory remains available even when no automatic template matches, including table/view SQL definitions, column types, primary keys, not-null constraints, foreign keys, indexes with uniqueness/origin/partial status and indexed-column order, index SQL definitions, and unavailable view errors. Search table, view, index, column, and SQL definition text across the inventory to adapt SQL manually in a large database; the same search narrows generated query templates by source name or SQL text. Then use **Use selected query template** to replace the editor query. Building or browsing templates leaves the current query untouched. Applying a template replaces the query and clears active SQL parameter values. The previous values remain as an inactive in-session draft with explicit restore or discard controls, available even when no query template is detected; restoring replaces active values and still requires validation. Changing the database path or loading another saved job discards that draft. Review and adjust the selected columns before validating or saving the query.

When preflight, validation, or a scheduled run reports `no such table`, `no such column`, or `ambiguous column name`, the Automation panel offers **Repair SQL** for the failed query. Saved-run repair loads the exact query and parameters when its configuration was recorded; preflight repair loads the saved job. Both start read-only schema discovery and leave any replacement template for review and explicit application. The editor identifies the originating run or preflight, error kind, and failed schema reference while you inspect the current schema and revise the query. It also compares the live schema with the latest saved capture for the same chart, database, and SQL series, listing added, removed, or modified objects and highlighting changed objects related to the failed reference. Dismiss the banner, cancel the edit, or save a successful repair to clear it. Older runs without recorded configuration fall back to the saved job. Run history marks the failure as **SCHEMA ADAPTATION NEEDED** with **Load configuration to repair SQL** beside the saved query; this action opens the same repair workspace. Run-time missing-table/column diagnostics compare the current schema fingerprint with the latest snapshot for the same chart and series and state whether schema drift is evidenced. Each diagnosis is persisted as structured run data with baseline availability, full baseline/current fingerprints when available, and separate schema, query, and typed-parameter change flags. `--list-runs --json` and automation outcome JSON expose it as `schema_diagnosis`; `--export-runs` includes a `schema_diagnosis_json` column. The status message remains available in the UI and run history. Without a prior fingerprint, the app says the cause cannot be determined. This helps distinguish schema drift from a changed or previously unverified query configuration. For missing tables or columns, the status suggests inspecting the current schema and rebuilding or editing the query; for an ambiguous column, it recommends qualifying the reference with its table or alias. Validate the repaired query before saving. The app does not rewrite saved SQL automatically. To adapt a saved job, choose **Edit**, inspect the database with **Build query from schema**, review the endpoint name/ID projections, and apply a template only after confirming it represents the intended relationship. Applying a template replaces the query and clears active SQL parameter values while keeping the previous values in an inactive in-session draft. Restore them only if they match the replacement query, then validate; changing the database path or loading another saved job discards the draft. Unused values are reported by query validation. Save the job only after the preview and capture limits pass. If an existing series already has captures, changing the query or base parameters requires a new series so comparisons do not mix definitions.

When **Repair SQL** opens schema inspection for a recognized SQLite error, the schema inventory search is prefilled with the failed table or column reference. The search narrows tables, views, indexes, columns, and generated templates so the likely schema change is immediately visible; clear or edit the search to browse the complete inventory.

When endpoint IDs have declared foreign keys to entity tables, generated queries join all columns in those keys and select a recognizable display field (and entity type when available), falling back to the scoped key as the endpoint label when no display field is recognized. When source and target display-name columns are already present, the query keeps those labels while still joining declared foreign keys for table-scoped identities and inferred endpoint types. Foreign-key IDs include the referenced table name and encode each SQLite storage type and hexadecimal value bytes, so equal local keys in different tables stay distinct and embedded NULs and separators remain unambiguous. Without a usable foreign key, the template falls back to direct endpoint columns or the endpoint IDs themselves. View schemas are inspected without reading records, allowing the builder to recognize source and target aliases exposed by analyst-authored views.

Schema discovery runs in the background so inspecting a large database does not block the desktop interface. It keeps usable tables available if a view has become invalid after a schema change. Unpreparable views are listed as unavailable with their inspection error; update or remove the stale view in the source database, or continue building a query from another object.

If a schema has no declared foreign keys, the builder infers an ID join only when one unambiguous entity-like table has a single primary key and a recognizable name column. Ambiguous schemas keep the endpoint IDs for manual query editing. Generated results retain endpoint IDs alongside display names so same-named source entities stay distinct and snapshots can match those identities over time.

SQL can return stable endpoint IDs as `source_entity_id`/`target_entity_id`, `source_external_id`/`target_external_id`, or common endpoint names such as `target_id`, `from_id`/`to_id`, `entity_a_id`/`entity_b_id`, `source_person_id`/`target_person_id`, `from_person_id`/`to_person_id`, `source_node_id`/`target_node_id`, and `from_node_id`/`to_node_id`. The `source_id` column name remains available for evidence references. These IDs preserve entity identity across captures when an entity’s display name changes.

When multiple tables or views match, the editor offers a source picker so you can choose which generated query to use. Candidates are ordered by endpoint identity projection coverage, declared endpoint joins, then recognized relationship fields, with object name as a deterministic tie-break; this puts structurally stronger candidates first without hiding alternatives. Confirm the projected identity expressions are stable source-system keys before applying a template. The CLI’s `query_template` is the highest-ranked candidate, and `query_templates` includes the full ranked list; the full schema remains available in `objects`.

Applying a generated template clears active parameter values. If values were present, the editor keeps them in an inactive in-session draft with explicit restore or discard controls. Restore them only after adding matching placeholders to the replacement query, then validate; unused values are reported by query validation.

## Configure jobs

Each saved job targets the chart that was open when the job was added. The Automation list shows its **Destination**, and the job editor has an explicit **Destination chart** selector. Editing from SQL Review, Sources, or another chart keeps the saved destination selected; change the selector to redirect future captures. Desktop, command-line, scheduled, and replay runs open the saved destination for ingestion, then restore the chart that was open before the run. The run record and immutable snapshot retain the destination chart ID. Reviewing a capture opens its destination chart when that chart still exists; highlighting a SQL source follows the selected capture to its chart. Comparisons, automation thresholds, and full-series exports use captures from the same database, series, and chart, so the same SQL source captured on two charts does not mix their histories. Older captures without a chart ID remain a separate legacy series because their original destination cannot be determined; the first chart-bound capture starts a new comparison baseline. If a saved destination chart was deleted, the run fails and records that failure. Older jobs without a saved chart ID continue to use whichever chart is open when they run.

Open **Automation**, enter a unique job name, SQLite database path, snapshot series, and query, then use **Validate query** to check the read-only query, returned connection count, and configured limits against the latest saved snapshot without saving case changes. A successful validation also previews up to eight returned connections so you can confirm the endpoint mapping before ingestion. The status distinguishes an invalid query from a valid query whose configured limits fail; `--validate-enabled-jobs` applies the same capture-limit assessment as a job run, while `--check-enabled-job-queries` checks query validity without enforcing those limits. Each database/series identity can belong to only one automation job; aliases to the same existing database file resolve to the same identity. This keeps one query stream from replacing another job’s chart links or mixing unrelated results in a comparison chain. Relative database paths resolve from the case file’s directory. Snapshots retain both the canonical database path and the configured path; when a case and its relative-path database move together, loading the case rebases its saved series, imported-link provenance, and SQL entity identity namespaces to the new location. When loading a case, paths in earlier snapshots are normalized too when their source databases are still available. Set **Minimum connections** to require a nonzero result size; the default of 0 disables this check. A result below the configured minimum is recorded as a failed run, while its successfully captured snapshot remains in history for review. Optionally enable **Limit connections** and set a maximum accepted result size; an oversized result is retained as a snapshot for review but the run fails. Optionally enable **Limit regressions** and set a maximum count; a regression is a removed connection or confidence decline versus the preceding snapshot in the same database/series. The baseline snapshot has no regressions to compare, and runs still save their snapshot and history when a limit is exceeded. Optionally set **Maximum relationship-property changes** or **Maximum entity-property changes** to fail captures when too many connections have changed connection properties or source/target attributes, respectively. These limits operate independently. Optionally set **Minimum connection confidence** from 1–3 to fail captures when any returned connection is below that score; the captured snapshot remains available for review. Optionally set **Limit skipped rows** and a maximum count to fail runs when the SQL result has too many rows with blank or NULL endpoints. The skipped-row count and threshold are retained with the run, while the successfully captured snapshot stays available for review. Add the job when it is ready. After a series has saved captures, changing that job’s query or base SQL parameters requires a new series; this keeps comparisons from mixing different query configurations while preserving the original history. The Automation list shows each job’s destination chart, latest run status, capture quality, connection/skipped-row counts, and duration. Use **Open destination** to switch to that chart, **Review latest capture** to open the newest saved SQL snapshot in SQL review, **View latest run** to filter and expand that exact run in history, or **View job history** to filter run history to every run from that job. Failed jobs also show a concise error summary inline; hover for the full result message. Search the list by job name, destination chart title or ID, database path, snapshot series, SQL text, or saved SQL parameters without changing saved jobs or run history. Expand **SQL query and capture configuration** to inspect a saved job without loading it into the editor. Use **Validate** beside a saved job to preflight its query and limits without changing the case; **Edit** loads its configuration into the editor. Enable the jobs you want included in a batch run. Filter the job list, then choose **Run visible enabled jobs and save** to run only the matching enabled jobs; the unfiltered **Run enabled jobs and save** action still runs every enabled job. Running an individual job or batch keeps the current editor fields intact. Each run records its status and timestamps in the case and appends a new immutable snapshot when the query succeeds. Save case and job edits before starting automation. Desktop runs execute on a background worker and show progress while pausing case editing; during capture, progress includes SQL result rows processed and blank-endpoint rows skipped. The worker holds the case lock and atomically saves each job checkpoint, including failed run records, so a slow SQL query does not freeze the window or lose completed work. One-off SQL validation and ingestion also run in the background; validation leaves the case unchanged, while ingestion updates the open case and still requires an explicit save. The command-line runner executes enabled jobs without opening the desktop UI and saves the updated case automatically:

Set the maximum to 0 to reject any skipped row. Older jobs default to no skipped-row limit. Expand a run in **Run history** to review its capture quality, connection and skipped-row counts, snapshot ID, and delta counts against the prior snapshot in that database/series. Use **Review changes** to open that exact capture against its immediately preceding capture, resetting custom baselines and filters so every change is visible. If the query text or effective SQL parameter values differ between the selected captures, SQL review flags the difference and lets you inspect both sets of inputs before interpreting the data changes.

Expanded run history also surfaces up to five removals, confidence declines, and entity or relationship-property changes inline, including their endpoints, relationship, evidence reference, and before/after values where available. **Show current** on a surviving connection focuses its chart link and preserves that run's capture as the selected SQL review; return with **SQL Review** to continue from the same comparison. Removed links remain available in **Review changes**, which opens the complete comparison with before/after details. Partial captures include a **PARTIAL DATA** review panel with a **Load captured query for validation** action. Use **Mark reviewed** to clear a run from **Unreviewed changes or partial data** without writing a comment, or **Reopen review** to put it back in that queue. Older cases still treat a saved analyst comment as reviewed until an explicit review state is recorded.

Enter one `name=value` per line in **SQL parameters** and reference it in the query with `:name`, `@name`, or `$name`. Unprefixed values bind as text; type a value with `text:`, `int:`, `real:`, `bool:`, or `null:` when SQLite should receive text, a 64-bit integer, a finite real, 0/1, or NULL. For example, use `snapshot_id=current`, `min_confidence=int:2`, and `include_unknown=bool:false`; `null:` binds SQL NULL and `text:null` binds the literal text `null`. Saved parameter values stay fixed across schedule runs. To roll a scheduled time window automatically, use SQLite date functions in the saved SQL, such as `event_date >= date('now', 'start of month', '-1 month') AND event_date < date('now', 'start of month')`; this selects the previous complete UTC calendar month. The [SQL ingestion example](sql-ingestion.md) shows the full query. Parameters are saved with the automation job, each immutable snapshot, and each run for reproducibility. For a one-off CLI run or preflight, repeat `--param name=value` to override or add parameter values without changing the saved job; these one-run overrides do not affect scheduled captures. For example, use `WHERE snapshot_id = :snapshot_id` with `snapshot_id=current`.

Use **Duplicate** on a saved job to start an unsaved draft with its query, parameters, destination, and capture limits. Arch Notebook assigns the draft a unique name and a new, collision-free series for the same database. **Save duplicate** adds it disabled with no run history; **Discard duplicate** drops the draft. Review the SQL and series, validate the copy, then explicitly enable and save it before scheduling or batch runs. Captures and run history remain with the original job.

## Run jobs from the CLI

Desktop batch runs announce a batch ID in the live progress view and save an atomic checkpoint after each job, then save the final batch summary. The Automation screen’s recent-batch panel shows completion counts, failed captures, jobs that need retry, effective typed SQL parameters, and schema-repair hints. Expand **Saved SQL configuration** for a job to inspect its saved database path, series, exact query, parameters, timeout, and limits before resuming. `--list-batches --json` also includes the recorded effective configuration for each selected job. Choose **Resume batch in app** to continue pending jobs from the saved manifest; completed captures are skipped. Each manifest retains the effective job definitions used to calculate its fingerprint, so overrides for jobs that had not started before an interruption remain available. If a later job or checkpoint step fails, the open app reloads the latest saved checkpoint and keeps the regression view focused on its newest snapshot. Desktop job and batch run IDs are retained with their completed-capture manifests and can be listed with `--list-batches`; `--resume-batch <batch-id>` reuses the saved job set and effective SQL parameters automatically. Optional `--job` selectors are checked against the manifest, and optional parameter overrides must still produce the exact saved configuration. Older manifests without effective definitions can still be resumed from the CLI using the original job selection and parameter overrides. The command-line runner also saves after each job, preserving completed run history if a later query stalls or the process is interrupted. Inspect a SQLite source before writing an ingestion query. This command opens the database read-only and lists its tables, views, column names, declared types, and key/required-column markers, followed by every generated relationship-query template it can recognize. Unavailable views include their preparation error; JSON output includes all templates in `query_templates`:

```sh
cargo run --offline -- --inspect-sqlite source.sqlite --json
```

Inspect SQLite's execution strategy before saving or scheduling a job. Choose **Explain draft plan** in the Automation editor for the current query, **Explain plan** beside a saved job, or use `--explain-job` from a script. Each path prepares the read-only query, binds its configured typed parameters, and asks SQLite for `EXPLAIN QUERY PLAN`; it does not execute the query, read connection rows, save run history, or change the case. Planning is interrupted after 30 seconds and reports a planning timeout, separately from the saved job's SQL query time limit. The desktop view shows the query and parameters used and discards a pending plan if the saved job or current draft changes. The desktop and text CLI indent plan steps by their parent structure; JSON includes each step's `depth`. The summary distinguishes unindexed scans, index-backed searches, and index-backed scans; JSON preserves `scan_steps` and adds `unindexed_scan_steps`, `indexed_search_steps`, and `indexed_scan_steps`. An unindexed scan is a planner hint, not an automatic failure: scans can be appropriate for small tables, and the plan does not measure runtime or actual row counts. Temporary one-run parameter values can be supplied with repeated `--param` options:

```sh
cargo run --offline -- --explain-job harbor-light.case.json "Harbor Light baseline" --param snapshot_id=current --json
```

Re-run the inspection after changing SQL or parameter values; SQLite may choose a different plan for the new query shape or values.

The JSON response uses schema version 1 and includes `ok`, `object_count`, table/view definitions, declared foreign-key mappings, index definitions, and `query_templates` for every table/view with recognizable source and target columns. The existing singular `query_template` field remains as the first candidate for compatibility. It reports structure only; it does not read table rows or modify the source. The text output reports when the database contains no user tables or views, lists declared foreign keys and indexes, and prints every generated query template.

To check enabled SQL queries and their SQLite sources without requiring current data to meet capture thresholds, use query-only preflight. It executes queries read-only and leaves the case unchanged; failing connection or regression limits are reported but do not fail the query check. A zero-connection result is still query-valid, but is classified as `empty_result` or `all_rows_skipped` and reported as having no usable connections, even when no minimum is configured. Desktop live checkpoints and run-history rows also show the result quality. Validation and query preflight acquire the per-case automation lock, so they wait for an active runner’s checkpoint and read a stable case snapshot. JSON output sets top-level `mode` to `query` and reports `query_valid`, `result_quality`, and `has_usable_connections` separately from each outcome’s normal run `status` and `capture_limits_pass`:

```sh
cargo run --offline -- --check-enabled-job-queries harbor-light.case.json
```

Add `--require-usable` to fail preflight when any selected query returns no usable connections. The Linux and macOS schedule installers use this check by default. In the desktop Automation schedule controls, turn off **Require usable connections before installing a schedule** only when an empty relationship capture is expected; this changes the install preflight, not scheduled run thresholds. The installers accept `ARCH_NOTEBOOK_REQUIRE_USABLE_CONNECTIONS=true|false` for the same choice and report the selected gate after installation. The CLI option does not enforce regression or capture thresholds; those remain visible runtime outcomes.

Preflight every enabled SQL job before scheduling a batch. Validation runs each query read-only, checks minimum and optional regression limits, and evaluates jobs in run order with a temporary snapshot chain. It does not save snapshots or change the case file:

```sh

```

Append `--json` for a machine-readable validation summary (`ok`, `saved`, pass/fail counts, and per-job outcomes). Batch execution also accepts `--json`; it prints the same summary shape after atomically saving snapshots and run history. Each executed batch outcome includes its persisted `run_id` (null for validation) and `duration_ms`, so callers can correlate failures without a snapshot, inspect query time, and reconcile outcomes with `--list-runs`. The desktop run history shows the same duration. The case is atomically updated after each completed job, so earlier outcomes survive if a later query stalls or the runner is interrupted. In JSON mode, standard output contains only one JSON result; errors that occur before a summary is available produce an `{ "schema_version": 1, "ok": false, "error": "..." }` object, while diagnostics also go to standard error. Successful results and JSON errors carry schema version 1. Failed jobs still return a nonzero process exit code. For example:

```sh

```

Run and validation JSON use schema version 1 and retain the existing per-job fields. Each outcome also includes a `schema_adaptation` object with `required`, `kind` (`missing_table`, `missing_column`, or `ambiguous_column`), the missing object or ambiguous column in `reference` when SQLite reports it, and a repair `hint` for those query errors, so scheduler integrations can route schema drift without parsing the human-readable message. Outcomes include observed-versus-required limit checks, snapshot identity and capture time, a typed delta summary, and changed connection facts with stable identity keys and prior values. The `limits.maximum_connection_property_changes` object reports the configured limit, observed changed-link count, and pass result; `connection_property_change_count` is also available at the outcome level. Snapshot deltas expose the same count as `delta.counts.connection_properties_changed`, with affected records carrying their before/current `connection_attributes`. The delta summary includes `configuration_changed` and per-field `configuration_changes` flags for SQL text and effective parameter values, allowing integrations to distinguish changed inputs from connection regressions. Direction changes are explicitly typed as `direction_changed` while still counting as `connection_updated` for compatibility. Downstream tools can evaluate regressions and inspect evidence changes without parsing the human-readable message. Automation CLI runs and desktop case saves coordinate through a per-case advisory lock. Concurrent CLI runs wait for the active runner; desktop saves compare the on-disk case with the version they loaded and reject stale writes, preserving newer automation checkpoints. ## Replay and resume

Replay a recorded automation run by its run UUID, including its saved query, parameters, and thresholds:

```sh
cargo run --offline -- --rerun-run harbor-light.case.json <run-id> --json
```

To check the same saved configuration against the current SQLite source without saving a snapshot or run, use `--validate-run` first:

```sh
cargo run --offline -- --validate-run harbor-light.case.json <run-id> --json
```

Validation leaves the case unchanged. Rerun saves a new run and snapshot, leaves the job definition unchanged, and reports `rerun_of` in JSON. Both commands work even if the original job was edited or removed, but reject older run records that did not preserve their configuration. Get the UUID from `--list-runs --json`.

Every `--run-job` or `--run-enabled-jobs` invocation announces its `batch_id` on standard error before running jobs and includes it in the JSON summary. Fresh CLI and desktop batches atomically save their manifest and effective job definitions before the first SQL query starts, so an interruption during that first query can still be inspected with `--list-batches` and resumed. Desktop job and batch runs show the ID in the live progress view. Both paths record completed captures with their PASS/FAIL result and retain the selected job IDs, names, and effective job definitions. If a process stops after saving some jobs, find the ID in the CLI announcement, desktop progress or `--list-batches --json` (or `--list-runs --json` while the run remains in history), then pass `--resume-batch <batch-id>`. New manifests restore the exact selected jobs and typed SQL parameters from the manifest; optional `--job` selectors are checked against the saved selection, and supplied overrides are accepted only when the resulting fingerprint matches. Older manifests without effective job definitions retain the previous behavior and require the same selected jobs and parameter overrides as the original run. Resume skips a job if that exact batch already saved its capture, even when the capture failed configured limits; the previous failure remains in the resume result and keeps the command unsuccessful. Jobs that failed before producing a snapshot and jobs that have not run are retried. The runner rejects a changed job selection or SQL configuration using a versioned SHA-256 fingerprint of the effective saved job definitions. Completed-capture checkpoints are stored separately from run history, so pruning the 200-record run history does not cause completed jobs to create duplicate snapshots. Cases retain the latest 200 batch manifests; `--list-batches` reports `COMPLETE`, `COMPLETE_WITH_FAILURES`, or `INCOMPLETE` with selected, completed, passed, failed, retry-required, and schema-adaptation counts. Completed failure entries include the same structured `schema_adaptation` object as run outcomes, plus run and snapshot IDs. Pending jobs include their latest run status/message and schema-adaptation signal when a failed attempt was recorded, so an operator can see a repair reason before resuming. Older manifests without a saved selection show **selection not recorded** rather than implying no jobs need retry. Older batches whose manifest has expired must be started as a fresh run. When resuming an older case without a batch manifest, the runner reconstructs completed captures from compatible retained run records. Skips appear in JSON as `skipped_jobs` and do not add snapshots or run history; if every selected job already has a completed capture, the case is not rewritten. Scheduled Linux and macOS runners use `--resume-incomplete-scheduled-batch`: it resumes only the latest scheduled batch when its recorded origin, job IDs, effective SQL configuration, and currently enabled jobs match, the batch has pending jobs, and the saved checkpoint proves no job attempt has failed. A failed-attempt marker is retained in the batch manifest even after run history pruning. Pre-change legacy manifests lack that proof and therefore start a new scheduled batch; operators can still resume them explicitly with `--resume-batch`. This protects current captures from stale job definitions and avoids silently retrying SQL failures. The switch is rejected outside a runner with `ARCH_NOTEBOOK_AUTOMATION_TRIGGER=scheduled`; ordinary CLI and desktop captures continue to start fresh batches.

Before a batch resumes, the desktop and CLI validate checkpoint uniqueness, ensure recorded completed-job IDs belong to the saved selection when available, confirm referenced snapshots still exist, and compare any retained run record with the checkpoint's job, batch, outcome, and snapshot. Run-history entries that have aged out remain valid because the batch checkpoint is retained separately. Inconsistent checkpoints are rejected instead of being treated as completed work.

```sh
cargo run --offline -- --run-enabled-jobs harbor-light.case.json --json
cargo run --offline -- --list-batches harbor-light.case.json --json
cargo run --offline -- --list-runs harbor-light.case.json --json
cargo run --offline -- --run-enabled-jobs harbor-light.case.json --resume-batch <batch-id> --json
cargo run --offline -- --run-job harbor-light.case.json "Harbor Light baseline" --param snapshot_id=current --resume-batch <batch-id> --json
```

For an unattended single-job pipeline, add `--export-chart-csv analyst-chart.csv` (or a `.tsv` path) to `--run-job`. The command writes the exact immutable capture produced by that run and adds `chart_csv_output` to its JSON outcome. A run that produces no snapshot creates no chart export; the case and run record are saved before export is attempted, so an export-path error does not discard the capture. This combines scheduled or command-line ingestion with a ready-to-map Analyst’s Notebook handoff:

```sh
cargo run --offline -- --run-job harbor-light.case.json "Harbor Light baseline" --param snapshot_id=current --export-chart-csv analyst-chart.csv --json
```

Use `--export-sql-chart-csv case.json <snapshot-id> analyst-chart.csv --json` when exporting an older capture or retrying a handoff separately.

Expand a row in the desktop history to inspect both sets. Select **Replay saved configuration** to run that exact saved SQL, parameters, and thresholds against the current SQLite source; replay appends a new run and snapshot without changing the job definition, and carries the original override provenance into the replay record. Use **Load configuration into editor** to revise a saved run before execution; if its original job was deleted or its current settings differ from the run (including one-run parameter overrides), the app opens a uniquely named recovered job draft instead of editing the current job. Saving adds the recovered draft disabled and filters the job list to it; choose a new series if the existing job still owns the run’s database/series, then review and enable it. The new run records the ID of the run it replayed, in both desktop history and `--list-runs --json` output. Older runs that predate this configuration capture are labeled as such rather than showing default values as if they were recorded settings. Successful runs include a comparison with the previous snapshot in the same database and series; the history records removed connections, confidence declines, date changes, additions, confidence increases, and other updates. Each snapshot has a stable ID, and automation run records link directly to it; older cases migrate those links from their saved snapshot indices when loaded. In the desktop app, use **Review snapshot #N** beside a run or select any numbered capture in **Snapshot history** to compare it with the preceding capture in that series; the capture number disambiguates runs recorded within the same clock interval. Use **Export capture CSV/TSV** beside a run to hand off that exact immutable capture with its query and parameter provenance, using the shared Export path. Batch summaries report passed and failed job counts. The runner continues through the selected jobs if one fails, saves each outcome, and exits nonzero when any job fails. Filter the desktop job list by name, destination chart, database, series, SQL, or parameters, then use **Run visible enabled jobs and save** to run only the enabled jobs shown without changing their enabled settings.

The run-history summary reports the visible count plus failure and unreviewed-failure counts for the current text and origin filters. The failure category toggles narrow the displayed rows without changing those scoped totals; review state uses the explicit review mark when present and the analyst comment as the fallback for older records. The top-level **Automation** tab shows an amber count for failed runs that remain unreviewed, including failures recorded by a scheduled run while the case was closed.

## Schedule recurring runs

In the desktop app, open **Automation** and select **Check schedule** to see whether the open case's timer or LaunchAgent is active, which cadence it uses, and whether chart CSV export is enabled. On Linux, status also reports the last and next timer dispatch when systemd provides those timestamps. A dispatch means the timer started the service; it does not prove the SQL jobs succeeded, so review the scheduled batch history for capture outcomes. The cadence, calendar run-time, weekly day, monthly day, usable-connection install-preflight policy, and **Chart CSV export folder** controls update to match the installed schedule for the case currently open; case switches reset them until you check the new case. Enter an existing absolute folder to enable one CSV per enabled job, or leave it blank to disable scheduled exports. Choose every 15 minutes, hourly, daily, weekly, or monthly, and set whether schedule installation must find at least one usable connection per enabled job; this safety check is on by default. Turn it off only when empty relationship captures are an expected result. Then select **Install/update schedule** to apply the settings. Daily, weekly, and monthly schedules accept a local 24-hour run time (`HH:MM`); weekly schedules default to Monday and can use any weekday, and monthly schedules can use any day from 1 through 28. Each case has its own schedule, so multiple cases can run independently; updating one case leaves other case schedules in place. The Automation panel summarizes the latest scheduled batch across its jobs, including failed and pending checkpoints. **Review scheduled failures** opens that batch's failed run records with the failed-run filter active; otherwise **View scheduled batch** opens its retained run history. Older records without a batch ID use **View scheduled run**. If a schedule runs while the desktop app is open, choose **Reload case** to read its newly written capture history from disk; unsaved edits prompt before reloading. The app uses the saved case, checks enabled SQL queries in read-only mode, and installs or updates that case's Linux systemd timer or macOS LaunchAgent. Save case and job edits before installing. Select **Remove schedule** to disable and remove the open case's schedule. To manage schedules manually, use the platform commands below.

The **Install/update schedule** control is disabled while a saved-job edit or duplicate draft is pending. Save or discard the editor first so the installed schedule uses the reviewed saved query. During installation, the Automation panel shows which saved SQL job is being preflighted and active-query progress before the scheduler is changed. Closing the window during a SQL capture cancels the active query and waits for its checkpoint; closing during schedule install, check, or removal waits for that operation to finish, while an active SQL preflight is cancelled first.

On Arch Linux with systemd, configure enabled jobs in the app, then install the hourly timer for the default case:

```sh
arch-notebook-install-automation
```

Pass a case-file path to schedule it; the path is canonicalized to assign a stable per-case unit or LaunchAgent ID. Set `ARCH_NOTEBOOK_AUTOMATION_SCHEDULE=15m`, `ARCH_NOTEBOOK_AUTOMATION_SCHEDULE=daily`, `ARCH_NOTEBOOK_AUTOMATION_SCHEDULE=weekly`, or `ARCH_NOTEBOOK_AUTOMATION_SCHEDULE=monthly` before running either platform installer to change the cadence; hourly is the default. For calendar schedules, set `ARCH_NOTEBOOK_AUTOMATION_TIME=HH:MM` in local 24-hour time; the default is `00:00`. Weekly schedules default to Monday; set `ARCH_NOTEBOOK_AUTOMATION_WEEKDAY` to `0` (Sunday) through `6` (Saturday) to select another weekday. Monthly runs use day 1 by default; set `ARCH_NOTEBOOK_AUTOMATION_MONTH_DAY` to a day from 1 through 28 to select another day. Rerunning an installer updates only that case's schedule. Both installers require at least one enabled job and use query-only preflight against each read-only SQLite source before creating or replacing that schedule. Current connection and regression limits remain runtime outcomes, so a real regression does not prevent its schedule from being installed. If query preflight fails, fix the job or make its database available; existing schedules remain active. Progress-enabled CLI runs report SQL rows processed and blank-endpoint rows skipped as the capture reads results, plus a 30-second heartbeat during long queries. Scheduled runs include job start and saved-completion status plus a heartbeat every 30 seconds during an active query. Linux sends this progress to the systemd journal; the macOS runner appends it to the case-specific rotated logs. These bounded status lines do not include full connection deltas; add `--json` to manual CLI runs when structured output is needed. The Linux installer writes user-owned, case-specific units under `${XDG_CONFIG_HOME:-$HOME/.config}/systemd/user` and enables or restarts the timer after preflight. It catches up a missed calendar run after the machine was offline and adds up to five minutes of randomized delay. User timers run only while the user systemd manager is active; to keep them running after logout and start them at boot, enable lingering for the account with `loginctl enable-linger "$USER"`. Each install prints its timer and service names. Check or remove one case with `arch-notebook-install-automation --status /path/to/case.json` or `--remove /path/to/case.json`; omitting the case path addresses only the legacy single schedule. On macOS, first open the app and enable jobs, then install the bundled LaunchAgent for the case:

```sh
app_bundle="/Applications/Arch Notebook.app"
bash "$app_bundle/Contents/Resources/install-macos-automation.sh" \
  "$HOME/Library/Application Support/Arch Notebook/harbor-light.case.json" \
  "$app_bundle"
```

After query preflight succeeds, the macOS installer creates and lints a case-specific LaunchAgent plist before unloading that case's previous agent. If the replacement cannot be loaded, it restores the prior plist and attempts to reload it. The agent runs once when loaded and then at the selected interval. The bundled runner keeps each case's logs private to the current account, rotates each at 5 MiB, and retains five older files under `~/Library/Logs/ArchNotebook/`; use the case schedule ID printed by the installer to locate the directory. Check or remove one case with `bash "$app_bundle/Contents/Resources/install-macos-automation.sh" --status "/path/to/case.json"` or `--remove "/path/to/case.json"`; omitting the case path addresses only the legacy single schedule. The LaunchAgent stores absolute paths to the app bundle, case file, and SQLite sources. If you move the app bundle or case file, reopen the app from its new location and reinstall/update the schedule. Keep the SQLite source available at the configured path when automation runs.
