# SQL snapshot ingestion

SQL query results may include `source_representation` and `target_representation` columns with `Icon`, `Theme line`, `Event frame`, `Box`, `Circle`, or `Text block` values. These optional aliases set the visual representation on captured entities; repeated rows for one entity must agree. Representation changes are included in entity-property snapshot deltas and are preserved in snapshot and chart CSV/TSV exports. Older snapshots without these fields continue to load.

**Build query from schema** also projects recognized representation fields from the relationship table or from joined endpoint tables, allowing saved SQL jobs to adapt to schemas that store display representation alongside entity records.

Template detection recognizes `src_name`, `src_entity_name`, `src_display_name`, `src_label`, and `src_id` for the source endpoint, with corresponding `dst_*` aliases for the target. It also recognizes `source_display_name` and `from_display_name`, plus `target_display_name` and `to_display_name`.

Manual SQL captures accept those endpoint name, type, representation, and ID aliases as well as the canonical `source`/`target` columns, so generated templates and hand-written queries use the same endpoint mapping conventions.

For custom property aliases such as `source_attribute:HomeAddress` or `connection_attribute:CaseNumber`, the captured property name keeps the alias spelling. Alias prefixes and duplicate-name checks are case-insensitive, so case-only duplicates on the same record side are rejected.

## Map relational records into a network

For a common transaction schema with `accounts(id, owner_name, institution)` and `transfers(id, sender_account_id, recipient_account_id, transfer_type, occurred_at, amount, status)`, join each event to its endpoint records and return one row per relationship. A disposable synthetic database matching this schema is provided in `archive/research.databases/relational_transfers.sql`:

```sh
sqlite3 /tmp/relational-transfers.sqlite < archive/research.databases/relational_transfers.sql
arch-notebook --inspect-sqlite /tmp/relational-transfers.sqlite --json
```

The schema builder recognizes the transfer table’s sender/recipient account foreign keys and uses `owner_name` for endpoint labels, so it can suggest a joined query from this fixture.

Generated queries use conventional relationship IDs when present. A generic `id` is used only when SQLite declares it unique; otherwise the builder uses the ordered primary-key columns or a complete non-partial unique index to create a deterministic table-scoped `connection_id`. Composite relationship keys therefore keep otherwise identical parallel records distinct across repeated captures.

`--inspect-sqlite --json` reports the SQLite schema version and deterministic schema fingerprint alongside the object inventory and detected query templates. Each template includes ranking signals for source/target identity coverage, a stable connection ID, declared endpoint joins, and recognized fields; use these signals to review why one candidate ranks above another. The fingerprint uses the same read-only transaction and calculation as saved snapshots, so scripts can compare it with the last capture before scheduling a run.

The query keeps account identity stable across refreshes, gives each transfer its own connection identity, and exposes fields for chart inspection and regression comparison:

```sql
SELECT
    sender.owner_name AS source,
    CAST(sender.id AS TEXT) AS source_entity_id,
    'Account' AS source_type,
    sender.institution AS "source_attribute:institution",
    recipient.owner_name AS target,
    CAST(recipient.id AS TEXT) AS target_entity_id,
    'Account' AS target_type,
    recipient.institution AS "target_attribute:institution",
    CAST(transfer.id AS TEXT) AS connection_id,
    transfer.transfer_type AS relationship,
    transfer.occurred_at AS date,
    3 AS confidence,
    1 AS directed,
    transfer.status AS notes,
    transfer.amount AS "connection_attribute:amount"
FROM transfers AS transfer
JOIN accounts AS sender
  ON sender.id = transfer.sender_account_id
JOIN accounts AS recipient
  ON recipient.id = transfer.recipient_account_id
WHERE transfer.occurred_at >= :start_date
  AND transfer.occurred_at < :end_date
ORDER BY transfer.occurred_at, transfer.id;
```

Set **SQL parameters** to `start_date=text:2025-01-01` and `end_date=text:2025-02-01` (one per line). The half-open interval includes the start and excludes the end, so adjacent monthly captures do not overlap. Reuse the query and snapshot series while changing the parameter values to compare periods. The transfer ID matches parallel transfers independently; the account IDs preserve endpoint identity even if an owner name changes. If source IDs are only unique within a tenant or database partition, include that scope in the entity ID expression, such as `CAST(transfer.tenant_id AS TEXT) || ':' || CAST(sender.id AS TEXT)`. Check that the source columns use compatible date formatting and that each connection ID is unique in the selected period before capture.

To walk through two periods, capture January with the values above, then capture February using `start_date=text:2025-02-01` and `end_date=text:2025-03-01` with the same database and series. To turn the query into a recurring job, save it from **Automation** with a stable series, then replace the two parameter predicates with SQLite's UTC calendar-month window. Remove the `start_date` and `end_date` values from **SQL parameters** before validating, because the recurring query no longer uses those bindings:

```sql
WHERE transfer.occurred_at >= date('now', 'start of month', '-1 month')
  AND transfer.occurred_at < date('now', 'start of month')
```

Each scheduled capture then reads the previous complete UTC month without changing the saved SQL text or parameters. The monthly cadence starts on day 1 at the configured local time, while SQLite’s `now` date functions use UTC; use it when the prior month’s source data is ready by then. If the feed finishes later, choose a daily cadence to retry the same previous-month window after it loads; run history retains each capture time and immutable query result for review. [SQLite date/time reference](https://www.sqlite.org/lang_datefunc.html).

SQL queries can also capture custom relationship properties by aliasing values as `connection_attribute:<name>`, for example `transaction.amount AS "connection_attribute:amount"`. They persist with immutable snapshots, appear in validation and before/after comparisons, and are included in snapshot and comparison CSV/TSV exports. Use the **Relationship properties** filter to isolate captures where these values changed. Properties appear in chart search and the selected-link inspector; SQL-owned values refresh from each query and are read-only there. The schema query builder recognizes columns prefixed `connection_attribute_` or `link_attribute_` and aliases them for capture.

### Inspect current source rows for a chart entity

In the selected entity inspector, expand **SQL source records** to see each saved database identity that has a matching SQL capture on the active chart. This keeps saved capture history separate from current source lookup. Arch Notebook preserves the same historical-versus-live distinction while keeping SQLite read-only. ## Review snapshots

The saved-series review table can filter regressions, endpoint identity changes, direction changes, evidence changes, source-note changes, or other updates, and search both sides of a change by connection ID/key, endpoint, type, date, evidence, notes, or custom endpoint properties. Filtering only changes the on-screen rows; the comparison export always includes every change. The export retains a readable `change` label and adds a boolean column for each change type, so spreadsheet filters and downstream tools can select exact regression categories. Before/current endpoint attribute JSON is included in comparison CSV/TSV and structured run deltas; the SQL Review table shows those properties side by side. Endpoint ID changes have a dedicated `entity_identity_changed` kind and filter while remaining included in `connection_updated`/`connection_details_changed` for existing consumers; before/current ID columns show the reassignment. Direction changes similarly have their own `direction_changed` category while remaining included in `connection_details_changed`. The `connection_key` column exposes the same stable ID or natural key used to match each record across snapshots, including when the source query does not provide `connection_id`. Structured automation deltas use this same normalized key in each connection’s `key` field.

For a removed connection, use **Show baseline endpoints** to focus and fit its former source and target entities on the chart when both still exist. Endpoints resolve by source identity first, then by a unique name/type match if that identity has changed; ambiguous matches are not guessed. This preserves a useful map of where the relationship disappeared without drawing the removed edge as if it were still current.

## Compare and export

In **SQL Review**, comparisons default to the immediately preceding capture in the selected database, series, and destination chart. Use **Compare with** to select any earlier capture in that same chart-specific series for longer-range analysis; the selected baseline changes the on-screen delta table and CSV/TSV export together.

### CLI snapshot export

Export one immutable SQL capture without opening the desktop app. The output contains the captured connection fields plus snapshot and destination-chart IDs, query, typed parameter values, SQLite schema version, and skipped-row count on each record. An empty capture still exports its header row. A `.tsv` or `.tab` output path selects tab-separated output; other paths use CSV. Export is atomic and refuses to overwrite the case file or any saved SQLite source.

```sh
cargo run --offline -- --export-sql-snapshot harbor-light.case.json <snapshot-id> capture.csv --json
```

Get a snapshot UUID from `--list-runs --json` or the saved case's snapshot records. The JSON response reports output format, capture counts, source key and paths, series, query, and typed parameter values, so an empty capture still has its complete provenance in the response.

Export a complete saved series by selecting any capture in that database/series. The CSV/TSV combines rows from every capture in case order, while the JSON response retains metadata for zero-connection captures too:

```sh
cargo run --offline -- --export-sql-series harbor-light.case.json <snapshot-id> series-history.csv --json
```

The output is atomic and refuses to replace the case or any saved SQLite source. This is useful for loading longitudinal capture rows into spreadsheet or analysis tools without exporting each capture separately.

### CLI comparison export

Export a saved SQL comparison without opening the desktop app by passing the baseline and current snapshot UUIDs. The snapshots must be ordered in the same saved database/series. A `.tsv` or `.tab` output path selects tab-separated output; other paths use CSV. Export is atomic and refuses to overwrite a saved SQLite source database.

```sh
cargo run --offline -- --export-sql-comparison harbor-light.case.json <baseline-snapshot-id> <current-snapshot-id> comparison.csv --json
```

The JSON response reports the output format, snapshot IDs, and number of changed records. Get snapshot UUIDs from `--list-runs --json` or the case’s saved snapshot records.

## Exchange data

CSV/TSV and comparison reports are written to a temporary sibling file and atomically replace the destination only after the full export succeeds. Delimited imports detect comma, semicolon, tab, or pipe separators from the first record outside quoted values; `.tsv` and `.tab` paths always use tabs. Imports also strip a UTF-8 BOM from the first header before column detection and resolve selected header names without case sensitivity, so spreadsheet header capitalization changes do not break saved import designs.

### GraphML, KML, and ANX

**Import GraphML** stages nodes and relationships through the validated import path; enable **Import into new chart** beside the exchange-import controls before starting CSV/TSV, GraphML, KML, or ANX import to isolate it from the active chart; the new destination is created only after staging succeeds. GraphML combines multiple top-level graphs into one case, flattens nested subgraphs while retaining each child entity’s `arch_notebook_parent_id` attribute, and imports recognized IDs, aliases, entity attributes, per-graph direction defaults, evidence, notes, and chart styling. GraphML key-level `<default>` values are applied to graph metadata, nodes, and edges that omit the property; explicit data takes precedence. Conflicting duplicate values for a node, edge, or graph property are rejected rather than silently overwritten. When GraphML omits `ingest_source`, the canonical input path identifies its source; edges without a connection ID or GraphML edge ID receive a stable ID from their source, endpoints, relationship, direction, and occurrence among identical parallel edges. This keeps ordinary edge identities steady when unrelated edges are reordered in the file. **Export GraphML** assigns edge IDs from source and connection identity and supplies a generated connection ID for local links that lack one, so exported relationships remain identifiable after reordering. It works with graph tools such as Gephi and Cytoscape and includes endpoint IDs, direction, labels, evidence, notes, confidence, source provenance, entity attributes, and chart styling. **Export KML** writes KML 2.2 points for entities with valid `latitude`/`lat` and `longitude`/`lon` (also `lng`, `long`, and `geo:lat`/`geo:lon`) attributes and line strings for links where both endpoints have coordinates; equivalent duplicate aliases are accepted, while malformed or conflicting aliases leave that entity unmapped. It carries entity attributes, external IDs, and link metadata. **Import KML** accepts KML 2.2 `Point` and `LineString` geometries, including a `MultiGeometry` with multiple line strings, through the validated import path. A multi-line placemark becomes one relationship record per line string, with a stable geometry suffix on its placemark and connection IDs. A placemark containing multiple points or mixed point and line geometries is rejected because its single identity cannot safely identify multiple entities. Point coordinates become latitude/longitude attributes. `ExtendedData` can carry entity or connection attributes, external IDs, direction, evidence, and endpoint IDs. Nested `Folder` names are captured as the `kml_folder_path` entity or relationship attribute and exported in `ExtendedData`. For external files without endpoint IDs, line endpoints are matched to unique point coordinates; unmatched or ambiguous coordinates fail with an actionable error. Other geometry types are reported as unsupported. **Import ANX** accepts UTF-8 and BOM-marked UTF-16 XML with one `ChartItemCollection`, maps supported entity shapes and links into the validated import path, preserves recognized Arch Notebook attributes, normalized chart coordinates, and standalone labels, and rejects unsupported chart-item forms instead of silently dropping them. Repeated connection IDs are retained and assigned deterministic per-record source scopes so the records remain distinct during import. Input is limited to 32 MiB and 100,000 chart items. These mappings and internal round-trip checks do not establish conformance with IBM's schema or application. Add coordinates through CSV/TSV entity attributes or SQL aliases such as `source_attribute:latitude` and `source_attribute:longitude`, then use the Chart toolbar or Data path controls, or run `arch-notebook --export-kml case.json chart.kml --json`. The JSON result reports mapped entities, exported relationships, and links lacking coordinates. When explicitly included, graph-level `source_catalog_json` maps each ingest-source key to its database and series, latest snapshot, SQLite schema version and schema fingerprint, exported link and distinct entity counts, and capture IDs with timestamps, SQLite schema versions, per-object schema fingerprints and column metadata, connection counts, and skipped-row counts. Per-object manifests include normalized fingerprints used to suggest probable renames; they contain no raw schema SQL. Imported source catalogs are associated with the destination chart and merged by chart plus source key; GraphML export of a selected chart includes only its associated catalogs. Legacy catalogs without chart ownership remain available for backward-compatible export. GraphML/KML are cross-tool interchange formats; CSV/TSV carries the full Arch Notebook case fields for round-trips. For scripts, import into an existing case or export without opening the desktop app:

```sh
arch-notebook --import-graphml case.json network.graphml --json
arch-notebook --import-kml case.json locations.kml --json
arch-notebook --import-anx case.json chart.anx --json
arch-notebook --export-graphml case.json chart.graphml --json
arch-notebook --export-anx case.json chart.anx --json
arch-notebook --export-graphml case.json selected-chart.graphml --chart "Chart title" --json
arch-notebook --export-graphml case.json provenance.graphml --include-source-catalog --json
arch-notebook --export-sql-chart-csv case.json <snapshot-id> analyst-chart.csv --json
```

GraphML export defaults to the active chart. Use `--chart <title-or-uuid>` to export another named chart without switching the desktop workspace; JSON output reports the selected chart ID and title. ANX export also accepts `--chart <title-or-uuid>` and writes UTF-16LE XML. It preserves Arch Notebook record IDs and custom fields as attributes while omitting local SQL source keys. Import and export both remain unverified against IBM's schema and application.

GraphML, KML, and ANX imports use the same validation and entity reconciliation as desktop import, lock the case against concurrent automation writes, and atomically save only after the full import succeeds. Their JSON response reports total entities and relationships in the updated case. GraphML export’s schema-versioned JSON response reports the output path, exported entity and relationship counts, and whether the SQL source catalog was included. The SQL source catalog is excluded by default because it can contain local SQLite paths and capture metadata. Pass `--include-source-catalog` or select **Include SQL source catalog** when the receiving workflow needs that provenance; `--omit-source-catalog` explicitly excludes it. Entity and relationship records are still exported.

## Stable identity and safety

Connections with a unique, stable `connection_id` are matched across snapshots by that ID. A query result with duplicate IDs is rejected so ambiguous rows cannot distort regression comparisons; SQL ingestion identifies both result rows in the error. Without an ID, the app uses a natural key from source, target, relationship, types, and direction; duplicate natural keys in one result are rejected, with both result rows reported, so include a unique ID when the source contains parallel connections with otherwise identical fields. Conflicting SQL entity attributes or visual representations also report both result rows. During CSV or SQL ingestion, entities are reconciled by name, a unique compatible alias, supplied type, and stable SQL source IDs. This keeps a merged entity connected to its imported records on refresh; changed source names for a stable ID are retained as searchable aliases without overwriting the chart label; ambiguous aliases remain separate for analyst review. Same-name entities of different types remain distinct while generic entities can gain a type from later imports.

### Read-only ingestion

SQLite connections open the configured source with `SQLITE_OPEN_READ_ONLY` and enable `PRAGMA query_only=ON` before preparing SQL. SQLite-classified writable statements are rejected before execution, and [query-only mode](https://sqlite.org/pragma.html#pragma_query_only) prevents database-file changes across the connection, including attached databases. The query cannot write to or create a database. Schema inspection and query-plan inspection use the same read-only connection setup. Each capture reads its timestamp and query results in one SQLite read transaction, so a concurrent commit cannot make the timestamp and rows describe different database states. Each attempt waits up to five seconds for a SQLite write lock; transient `SQLITE_BUSY` or `SQLITE_LOCKED` errors retry up to three total capture attempts with two-second pauses, helping scheduled captures run through short source updates. A saved SQL job has a configurable per-query execution limit from 1 to 1,440 minutes, defaulting to 15. A timeout is recorded as a failed run and interrupts the active query so it cannot hold the case lock indefinitely. Scheduled Linux batches have no aggregate service timeout, so every enabled job can finish even when the total batch takes longer than an hour; each query uses its own saved limit.
